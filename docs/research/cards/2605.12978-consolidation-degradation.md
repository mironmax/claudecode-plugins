# Useful Memories Become Faulty When Continuously Updated by LLMs

arXiv [2605.12978](https://arxiv.org/abs/2605.12978) v2, 29 Aug 2026. Zhang et al., UIUC.

**Claim.** When an LLM repeatedly rewrites a consolidated textual memory
store, its usefulness rises and then falls, sometimes below having no memory.
The cleanest case: on a 19-problem ARC-AGI slice that GPT-5.4 solves at 100%
without memory, streamed consolidation from ground-truth solutions brings it
"down to 54%" (Fig. 2 caption: 52.6% by round 10). A one-pass consolidation
of the same pool stays at 100%.

**Conditions.**
- Models: GPT-5.4, GPT-5.4-mini, GPT-5-mini, GPT-5-nano, Qwen3.5-{4B,9B,27B},
  Claude Haiku 4.5, Claude Sonnet 5, plus an OpenCode agent on GPT-5.5,
  Claude Sonnet 5, GLM 5.2 and DeepSeek V4 Pro.
- Tasks: ALFWorld, ScienceWorld, WebShop, AppWorld, Mind2Web, and a
  synthetic ARC-AGI Stream with known task families.
- Memory: procedural "lessons" distilled from trajectories (CLIN, AWM,
  Dynamic Cheatsheet, ACE, and seven frameworks in total). All entries are
  placed in context at evaluation.
- Who writes, and when: an LLM consolidator, after every batch (Stream), or
  once over the whole pool (Static).
- Horizon: up to 400 steps on ARC-AGI Stream; about 100 steps on
  ScienceWorld.
- Mechanism (Table 5, GPT-5.4, batch 1, step 400): default in-place rewriting
  scores 43.2. Append-only with the prior store visible scores 50.0.
  Add+delete without in-place edits scores 64.0. Append-only with the prior
  store hidden scores 70.0. Raw trajectories score 76.6.

**Applicability: partially.** This is the one study that isolates in-place
rewriting of stored content as the most damaging single step. That is exactly
what the `gist` and `notes` chores do (`server/core/chores.py`,
`_KIND_INSTRUCTIONS`), although here a given node is rewritten rarely, not
after every interaction. The paper's memory is procedural and benchmark-fed.
This plugin's memory is mostly declarative and human-steered, and prior node
versions survive in the storage root's git history. The model reading the
graph never sees those prior versions, however.

**What it would change here.** It supports the churn guard in task 03.
Testable: rebuild each node's gist-rewrite count from storage-root git
history, then compare how often nodes with 0, 1 and ≥3 rewrites are endorsed,
using `useful.jsonl` and controlling for how often each was surfaced
(`recall.jsonl`). The prediction from this paper is a falling rate at high
rewrite counts. A flat rate would indicate that single-node, low-frequency
rewriting sits outside the regime studied.

**Verification.** Full read of the main body (§1–7); appendices not read.
The abstract says GPT-5.4 "fails on 54%" of the previously solved problems,
while the body says accuracy falls *to* 54% (fails on ~46%). The two
statements disagree; the body's figure is used above.
