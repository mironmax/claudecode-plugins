# Your Agents Are Aging Too: Agent Lifespan Engineering for Deployed Systems (AgingBench)

arXiv [2605.26302](https://arxiv.org/abs/2605.26302) v1, 25 May 2026. *Addition to the starting corpus.*

**Claim.** Deployed agents with frozen weights still degrade, through four
separable mechanisms: compression, interference, revision and maintenance.
Routine lifecycle events produce abrupt, model-specific regressions: a
post-event shock of −0.50 for Gemma4-31B after a history flush under careful
compression, and −0.21 for Haiku-4.5 in Claude Code after a workspace
migration. Behavioural compliance can stay clean while factual precision
decays.

**Conditions.**
- Models: 14, from 7B to 120B open models plus GPT-4o/4o-mini/5-mini and
  Claude Haiku 4.5, Sonnet 4.5/4.6 and Opus 4.7.
- Frameworks: ReAct with runner-managed compaction memory (Tier 1);
  OpenHands and Claude Code managing their own workspace files (Tier 2).
- Tasks: seven programmatically generated scenarios with a temporal
  dependency graph (version chains, confusable pairs, accumulators) and
  lifecycle events injected at set sessions.
- Diagnosis ladder: P1 is the agent as-is; P2 uses oracle retrieval over the
  agent-written store; P3 gives oracle context. Utilization error is 1−P3;
  write error is P3−P2; read error is P2−P1.
- Horizon: the abstract says 8–200 sessions; §6.1 says "8–12 sessions on
  S1–S6 and 10-block runs for S5/S7".

**Applicability: partially.** Maintenance aging is this plugin's concern:
chores, compaction to the archive, and refill all act on the store between
sessions. The benchmark's Tier 1 memory is a single compacted summary
rewritten every session, which is closer to the regime in 2605.12978 than to
itemized nodes. In Tier 2, where agents manage their own files, workspace
fidelity exceeds recall in every configuration. Correct answers involve more
re-reading, which places that gap at utilization rather than storage.

**What it would change here.** Two testable additions to task 02:
1. An approximate P-ladder for dug-up endorsements. Was the node archived at
   prompt time (a store/write miss)? Active but unmatched in `recall.jsonl`
   (a retrieval miss)? Or already injected earlier in the session and still
   dug up (a utilization miss)?
2. A maintenance-shock window: compare the endorsement and recall rates of
   nodes a chore touched, before and after the `chores.jsonl` timestamp.
